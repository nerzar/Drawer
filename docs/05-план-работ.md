# План работ Drawer

Это текущий план развития программы. Подробная история старых этапов остаётся в Git и старых отчётах; здесь только то, что ещё имеет смысл делать дальше.

Главное правило: если этот план расходится с `PRODUCT_SPEC.md` или свежим решением владельца, приоритет у `PRODUCT_SPEC.md` и решения владельца. При непонятном поведении нужно спросить владельца, а не додумывать.

## 1. Сначала стабилизировать текущее поведение

`master` — самая стабильная текущая версия, но в ней ещё есть баги.

Ближайшая цель — исправлять реальные проблемы небольшими кусками и сразу проверять их там, где это проще увидеть руками.

Особенно внимательно относиться к:

- нескольким мониторам;
- кромкам;
- показу и скрытию окон;
- фокусу, Alt+Tab и панели задач;
- анимации;
- Settings.

Не накладывать несколько изменений поведения друг на друга до проверки предыдущего.

## 2. Анимация

Известная проблема: если окно должно выезжать со стороны, за которой физически находится соседний монитор, обычный slide показывает часть анимации на соседнем экране.

Нужно отдельно исследовать способ анимировать появление **внутри целевого монитора**, не двигая настоящее окно через соседний экран.

Первый кандидат для прототипа — DWM Thumbnail: Drawer показывает временное визуальное представление окна и анимирует его внутри нужного монитора. Это потенциально подходит не только для slide, но и для reveal, fade, zoom и смешанных эффектов.

Запасной простой вариант — clipping через `SetWindowRgn` для reveal-анимации.

Сначала сделать маленький отдельный прототип, не менять production-код Drawer. Результат проверить визуально. Только после этого выбирать технический способ.

## 3. Довести Settings

Settings уже в основном работают, но их нужно привести к текущему продуктовому контракту и ещё раз проверить реальные сценарии.

Нужно:

- убрать из обычного UI технические параметры, которые пользователь не должен настраивать напрямую;
- сохранить пользовательскую настройку «Убирать окно, когда фокус ушёл»;
- проверить постоянные и динамические слоты;
- проверить «Сделать постоянным», «Сделать временным» и «Сбросить слот»;
- проверить выбор приложения/окна;
- убедиться, что Settings и контекстное меню кромки вызывают одни и те же действия, а не отдельные реализации;
- сохранить `config.ini` единственным постоянным источником настроек.

Изображения в `PRODUCT_SPEC.md` пока не обязательны. Если для UI-решения нужен визуальный эталон — спросить владельца.

## 4. Продолжить разбор большого `drawer.ahk`

Монолит нужно уменьшать, но только небольшими безопасными шагами.

Цель — не просто раскидать функции по файлам, а сделать понятные части программы с простой ответственностью.

Центральная модель слота уже вынесена в `Slots.ahk`.

Дальше по очереди можно отделять:

- работу с окнами и фокусом;
- парковку и геометрию;
- кромки;
- Settings;
- tray.

Каждый такой шаг должен быть отдельным небольшим изменением без изменения пользовательского поведения. После неудачной ночной волны не пытаться снова вынести несколько больших частей одновременно.

## 5. После стабилизации — развитие слотов

Когда основное поведение и границы модулей снова стабильны:

- убрать фундаментальное ограничение на 9 слотов;
- добавить создание и удаление слотов через Settings;
- сделать хоткей обычным свойством слота;
- для первых девяти сохранить привычные `Ctrl+Alt+1…9` по умолчанию;
- развить контекстное меню кромки;
- постепенно расширить tray.

Не добавлять функции только потому, что их «можно сделать». Сначала нужна понятная пользовательская польза.

## 6. Что пока отложено

Пока не приоритет:

- установщик;
- автозапуск;
- Linux;
- полноценное управление раскладкой окон;
- сложный выбор конкретного документа/вкладки внутри приложения;
- дополнительные глобальные команды вроде Hide all / Show all;
- поиск и фильтр слотов.

## 7. Тесты и ручная проверка

Автотесты нужны, когда они быстро ловят конкретную техническую ошибку.

Не нужно превращать каждое изменение в длинную цепочку тестов и взаимных review разных агентов.

Для окон, фокуса, нескольких мониторов и анимации ручная проверка владельца часто быстрее и полезнее.

Если пользователь уже показал конкретную регрессию, сначала исправлять её минимально, а не строить вокруг неё новый большой тестовый контур.

## 8. Git

Работу вести аккуратно:

- отдельная понятная ветка для отдельного изменения;
- не смешивать несвязанные правки;
- не трогать пользовательские изменения;
- после завершения удалять ненужные рабочие ветки и worktree, если в них не осталось уникальной работы;
- не плодить временные сущности без необходимости.

Актуальное состояние веток, SHA и задач брать из Git, а не из старых документов или памяти.
