# Drawer — Product & Behavior Specification

**Статус:** отредактировано владельцем; визуальные эталоны ещё не добавлены  
**Эталон поведения:** этот документ; для уже существующего поведения, не переопределённого здесь, trusted runtime baseline — `6bfa010fbf0ca7e1b47e856b7c13a450ff54b1fa`  
**Владелец продукта:** пользователь

Этот документ описывает **что должен делать Drawer**, а не как это реализовано. Код, тесты и архитектурные решения не должны менять описанное здесь поведение без явного решения владельца.

## 1. Что такое Drawer

Drawer держит выбранные окна приложений в «карманах» за краем экрана и позволяет быстро выдвигать/прятать их хоткеем или через кромку. Окно не закрывается и не сворачивается, его рабочее состояние сохраняется.

Основной сценарий: VS Code / PhpStorm / браузер / терминал доступны напрямую, без поиска через Alt+Tab.

## 2. Слоты и хоткеи

Есть 9 слотов: `1…9`.

- `Ctrl+Alt+N` — показать/спрятать окно слота N.
- `Ctrl+Alt+Shift+N` — назначить активное окно в динамический слот N.
- Постоянный слот задаётся `[slotN]` в настройках и динамически не перезаписывается.
- Динамическая привязка живёт до закрытия окна, очистки или перезапуска Drawer.
- `Ctrl+Alt+0` — очистить динамические привязки.
- `Ctrl+Alt+Shift+0` — полный сброс.
- Отдельного целевого `focusHotkey` нет: у слота один основной хоткей показа/скрытия.

## 3. Показ, скрытие и активация окна

При показе окно выезжает из настроенного края (`left/right/top/bottom`) на заданную долю рабочей области монитора.

При скрытии окно уезжает за край, но остаётся живым. Повторный показ возвращает то же окно с его состоянием.

- В обычных Settings пользователь выбирает **скорость и вид анимации**, а не редактирует технические `animMs` / `animSteps`.
- Сейчас частично реализован только вариант выезда; другие виды анимации — отдельное развитие продукта.
- Анимация скрытия должна быть заметно быстрее анимации появления: ориентир — примерно в 2–3 раза, чтобы пользователь мог быстро переключаться между окнами и не ждать ухода предыдущего.
- Если за выбранным краем расположен другой монитор, окно не должно видимо проезжать по соседнему экрану. При этом анимация появления на активном целевом мониторе должна сохраняться.
- При обычном вызове слота окно после появления становится активным рабочим окном.
- Не требуется жёсткая политика «вернуть фокус строго предыдущему окну» при скрытии. Drawer не должен создавать странные или неожиданные скачки фокуса.

### Единый Show

У Drawer один пользовательский механизм показа слота. Его могут вызвать:

- `Ctrl+Alt+N`;
- левый клик по кромке;
- выбор припаркованного окна через `Alt+Tab`;
- клик по его кнопке на панели задач Windows.

Во всех случаях должен происходить тот же Show слота с поведением Drawer. Не должно быть отдельного сценария, где Windows визуально разворачивает окно из панели задач, после чего Drawer тут же прячет или перемещает его обратно.

## 4. Мониторы — НЕ МЕНЯТЬ БЕЗ РЕШЕНИЯ ВЛАДЕЛЬЦА

Есть два режима выбора монитора.

### `monitor=cursor`

Это **динамический режим**.

- Кромка следует за монитором, на котором сейчас находится курсор.
- Управляемое окно следует за монитором курсора.
- При Show используется **текущий** монитор курсора.
- Монитор первоначального bind не закрепляется за окном.
- Перевёл курсор на другой монитор → следующий Show и кромка работают на этом мониторе.

### `monitor=1/2/3…`

Окно и его кромка закреплены за явно выбранным монитором, а не следуют за курсором.

Поведение при физическом отключении закреплённого монитора пока не является отдельным утверждённым контрактом и не должно додумываться агентами без решения владельца.

Количество, расположение и разрешение мониторов заранее не предполагаются; геометрия берётся у Windows.

## 5. Кромки

Кромка — маленькая плитка у края экрана для припаркованного окна.

- Показывает иконку приложения.
- При наведении увеличивается и показывает номер слота.
- Левый клик действует как `Ctrl+Alt+N`.
- Кромка должна оставаться доступной поверх обычных и развёрнутых окон.
- Для `monitor=cursor` кромка перемещается между мониторами вслед за курсором вместе с соответствующим поведением окна.
- Размер кромки задаётся в General Settings.
- `handles=false` полностью отключает кромки и связанный с ними опрос мыши.

### Правый клик по кромке

Открывает контекстное меню:

- **Сбросить слот**;
- **Сделать постоянным / Сделать временным** — в зависимости от текущего типа;
- показать хоткей слота;
- **Изменить…** — открыть Settings сразу на этом слоте.

Эти команды не имеют отдельной логики: они выполняют те же действия, что соответствующие команды в Settings.

### Визуальный эталон

Скриншот утверждённой кромки будет добавлен отдельно.

## 6. Постоянные и динамические слоты

### Постоянный слот

Привязан к приложению через настройки и сохраняет тип/привязку после перезапуска Drawer.

### Динамический слот

Привязывается к текущему активному окну через `Ctrl+Alt+Shift+N`. Привязка окна временная, но индивидуальные настройки слота могут сохраняться.

### Изменение типа и сброс

- Поведение **«Сделать постоянным»** и **«Сделать временным»** уже реализовано в актуальной локальной версии; при документировании и переносе использовать существующую пользовательскую семантику, а не проектировать новую.
- **Сбросить слот** уже реализован: убирает приложение и возвращает настройки этого слота к значениям по умолчанию.
- Те же операции из контекстного меню кромки и из Settings должны быть одним и тем же продуктовым действием.

## 7. Состояния слота

Базовые состояния:

- **Пустой** — окно не привязано;
- **Припаркован** — окно управляется Drawer и скрыто;
- **Показан** — окно управляется Drawer и находится на экране;
- **Приложение не запущено** — состояние постоянного слота, когда настроенное приложение сейчас отсутствует.

Конкретные пользовательские подписи могут уточняться, но логическая модель состояний должна оставаться однозначной.

## 8. Settings

Settings — графическая оболочка над `config.ini`, а не отдельное хранилище.

Пользователь настраивает:

- скорость / вид анимации;
- кромки и их размер;
- постоянные и динамические слоты;
- приложение / имя слота;
- monitor;
- edge;
- размер панели;
- скрытие неактивного окна;
- настройки конкретных слотов и значения по умолчанию для динамических слотов.

В обычном UI не нужны:

- `blur interval` как технический интервал опроса;
- отдельный `focusHotkey`;
- технические `animMs` / `animSteps`.

Отдельную настройку «Фокус при показе» пока не вводить: базовое ожидаемое поведение — показанное через Drawer окно становится активным рабочим окном. Отображение поверх остальных окон и keyboard focus — разные технические понятия; не создавать пользовательскую опцию, пока для неё нет отдельной продуктовой необходимости.

Изменения записываются только по явному Apply/OK; `config.ini` остаётся постоянным источником настроек.

### Визуальный эталон

Утверждённые скриншоты Settings будут добавлены отдельно.

## 9. Tray и жизненный цикл

Минимальный tray сейчас:

- **Settings**;
- **Exit**.

Дополнительные пункты могут появиться позже.

Также:

- Drawer запускается один раз и работает в фоне весь день;
- второй экземпляр вытесняет старый, а не оставляет два конфликтующих процесса;
- явный Exit должен вернуть управляемые окна в нормальное доступное состояние;
- ошибка/закрытие одного управляемого окна не должна валить Drawer.

## 10. Один продуктовый action — несколько точек входа

Одинаковое пользовательское действие не должно иметь разные варианты поведения в разных частях программы.

Примеры:

- Show слота одинаков для хоткея, левого клика по кромке, Alt+Tab и панели задач;
- Reset одинаков из Settings и контекстного меню кромки;
- «Сделать постоянным / временным» одинаково работает из Settings и кромки.

UI может иметь несколько точек входа, но продуктовая операция должна оставаться одной.

## 11. Что считается регрессией

Без явного решения владельца нельзя:

- закреплять `monitor=cursor` за монитором первоначального bind;
- менять направление/характер Show/Hide;
- позволять анимации визуально проезжать через соседний монитор;
- делать кромку недоступной из-за обычного развёрнутого окна;
- менять смысл существующих хоткеев;
- создавать разные варианты одного действия для Settings / кромки / хоткея / внешней активации;
- считать зелёный unit/seam test достаточным основанием для изменения пользовательского поведения.

## 12. Приёмка изменений

1. Сравнивать поведение с этим документом.
2. Для существующего поведения, которое документ ещё не переопределил, сверяться с trusted baseline `6bfa010...`.
3. Любая неоднозначность поведения → вопрос владельцу, а не новое архитектурное решение.
4. Runtime-sensitive изменение → короткая ручная проверка пользователем до следующего такого изменения.
5. Рефакторинг должен быть behavior-neutral: если поведение изменилось, это не «просто рефакторинг».
