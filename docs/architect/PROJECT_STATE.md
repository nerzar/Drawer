# Drawer — текущее состояние

Актуально на 10 сентября 2026.

## Сейчас

- `master` — текущая наиболее стабильная рабочая версия после ручной проверки и последней сборки. Это **не эталон**: известные и неизвестные баги остаются.
- Поведение продукта определяется `docs/PRODUCT_SPEC.md` и явными решениями владельца.
- Ночная волна больших рефакторингов привела к регрессиям multi-monitor, кромок, геометрии и поведения окон. Не возвращать её целиком и не считать старые зелёные тесты доказательством корректности.
- Muse доступен постоянно и может использоваться в любой момент. Ранее владелец временно вывел его из работы только для разбора неудачной волны.
- Antigravity/OpenCode используются, когда для них есть понятная задача.

## Анимация — закрыто

Проблема соседнего монитора (окно с краем в сторону другого экрана раньше показывало часть slide-анимации на нём) решена переводом показа/скрытия на Windows DWM Thumbnail: настоящее окно остаётся в безопасном положении, Drawer анимирует его визуальное представление внутри целевого монитора (`AnimationDwmShow`/`AnimationDwmHide` в `src/drawer.ahk`). Это в production, а не PoC. `reveal` остаётся отдельным стилем через `SetWindowRgn`-clip.

Новые находки по анимации фиксировать отдельным пунктом в `docs/05-план-работ.md`, когда появятся — общего открытого направления исследования сейчас нет.

## Что уже решено владельцем

- `monitor=cursor` остаётся динамическим: окно и кромка следуют за монитором курсора.
- Можно явно закрепить слот за конкретным монитором.
- Показ слота через хоткей, кромку, Alt+Tab и панель задач должен приводить к одному пользовательскому действию Show.
- Показанное окно становится активным рабочим окном.
- «Убирать окно, когда фокус ушёл» остаётся пользовательской настройкой; при выключении пользователь скрывает окно вручную.
- Кромка должна быть доступна поверх развёрнутых окон; ПКМ открывает меню управления слотом.
- Сброс слота удаляет приложение и возвращает настройки слота к значениям по умолчанию.
- Технические `blur interval`, `focusHotkey`, `activateOnShow`, `animMs/animSteps` не нужны в обычном UI.

## Долгосрочный план

Подробный незавершённый roadmap уже существует в `docs/05-план-работ.md`. Новый архитектор должен обязательно прочитать его при старте и сверить с более свежим `PRODUCT_SPEC.md` и решениями владельца: старый план может содержать устаревшие детали, но его незавершённые направления нельзя потерять.

Ключевые направления оттуда:

- завершение и ручная приёмка Settings;
- продолжение модульного рефакторинга исторического `src/drawer.ahk` небольшими behavior-neutral кусками: оконная модель/фокус, parking, handles, settings, tray;
- у каждого вынесенного модуля должна быть понятная граница и короткий контракт, а не просто перенос функций по файлам;
- после стабилизации границ — произвольное количество слотов и дальнейшие UI-действия;
- отложенные возможности и технический долг стенда не смешивать с ближайшими runtime-исправлениями.

## Ближайший порядок работы

1. Использовать `PRODUCT_SPEC.md` как основной продуктовый контракт. Изображения пока не обязательны; если для решения нужен визуальный эталон — спросить владельца.
2. Перезапустить архитектора в чистом сеансе с коротким контекстом и долговременной памятью.
3. Новый архитектор читает также `docs/05-план-работ.md`, чтобы не потерять ранее согласованный roadmap, и отмечает противоречия со свежим продуктовым контрактом вместо молчаливого выбора одной версии.
4. Перед новой разработкой привести `AGENT_BOARD.md` к текущему состоянию `master` и `PRODUCT_SPEC.md`.
5. Дальше исправлять и развивать программу небольшими проверяемыми кусками. Git вести аккуратно и понятно: не плодить лишние ветки/сущности и убирать завершённые рабочие ветки после безопасной проверки.
6. Для поведения реальных окон, фокуса, анимации и нескольких мониторов использовать короткую ручную приёмку владельца, когда она быстрее и надёжнее дополнительного круга агентских тестов.
