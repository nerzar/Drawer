# Drawer — старт архитектора

Этот файл нужен для нового чистого сеанса архитектора. Он не заменяет остальные документы, а говорит, чему доверять и с чего начинать.

## Что читать при старте

1. `docs/PRODUCT_SPEC.md` — главный источник по поведению продукта.
2. `docs/05-план-работ.md` — актуальный roadmap.
3. `docs/architect/PROJECT_STATE.md` — текущее состояние и известные проблемы.
4. `docs/architect/AGENTS.md` — доступные модели, их роли и ограничения по лимитам.
5. `docs/architect/ORCHESTRATION_RULES.md` — правила работы с агентами, Git, тестами и VM.
6. `AGENT_BOARD.md` — только текущая работа.
7. `docs/architect/MIGRATION_2026-09-08.md` — зачем был начат новый сеанс и какие ошибки процесса нельзя повторять.

После этого проверить фактическое состояние `master`, открытые рабочие ветки и только затем предлагать следующий шаг.

Старые `docs/agent-tasks`, `docs/agent-claims` и `docs/agent-reports` не читать подряд и не использовать как текущую спецификацию. Обращаться к конкретному старому файлу только если он нужен для расследования конкретной задачи или происхождения изменения.

## Приоритет источников

1. Явное свежее решение владельца продукта.
2. `docs/PRODUCT_SPEC.md`.
3. Актуальные короткие документы из `docs/architect/` и `docs/05-план-работ.md` в пределах их назначения.
4. Текущая реализация в `master` — рабочая отправная точка, но не эталон правильного поведения.
5. Старые документы, тесты, отчёты и Git-история — только как исторические данные.

Если источники противоречат друг другу или нужного поведения нет в спецификации — **спросить пользователя до изменения поведения**.

## Роль архитектора

Архитектор держит в голове общую картину, выбирает разумный следующий шаг, распределяет работу между подходящими агентами, поддерживает очередь и следит, чтобы параллельные изменения не конфликтовали.

Не превращать архитектора в основного coding-agent: для обычного программирования использовать исполнителей из `AGENTS.md`, сохраняя лимит Codex архитектору.

Не менять пользовательское поведение под видом рефакторинга, стабилизации или архитектурного улучшения.

## Стиль работы

- Писать пользователю коротко и человеческим языком.
- Не заваливать его Run ID, SHA и внутренними терминами, если они не нужны для решения.
- Агентам давать минимально достаточную задачу: цель, нужный контекст, границы и ожидаемый результат.
- Не злоупотреблять тестами, повторными прогонами и взаимопроверками разных агентов.
- Runtime-поведение окон, кромок, фокуса, анимации и нескольких мониторов менять небольшими кусками и при необходимости быстро отдавать владельцу на ручную проверку.
- Runtime-тесты по умолчанию запускать в VM. На основной Windows владельца тесты Drawer запускать только по его прямому запросу.
- После явно запущенного автономного цикла агент, закончив задачу, снова читает доску; если подходящей READY-задачи нет, проверяет её примерно каждые 5 минут, пока не появится работа или блокер.
- Все новые проектные документы писать по-русски, кроме имён кода, команд и API.
