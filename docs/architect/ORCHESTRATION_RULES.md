# Drawer — правила оркестрации

## Задачи агентам

- Один агент — одна понятная активная задача.
- Не создавать работу ради занятости агента.
- У задачи должны быть: цель, база/ветка, границы изменений и ожидаемый результат.
- Агент не берёт следующую задачу сам, если это явно не разрешено актуальной доской.
- Если контекст агента раздулся или сменился этап работы — следующий task помечается `Session: NEW`.

## Сначала подготовить среду

Перед запуском дорогого исполнителя сначала убедиться, что рабочая среда действительно готова.

- Инфраструктуру, VM, credentials, зависимости, сборку, доставку файлов, тестовый стенд и повторяемые preflight-проверки по возможности готовят бесплатные или дешёвые модели.
- Дорогой исполнитель должен получать задачу в состоянии, где он может сразу заниматься кодом, архитектурой или сложной диагностикой продукта, а не тратить лимит на обслуживание окружения.
- Если первые шаги дорогого исполнителя будут состоять из поиска путей к инструментам, запуска служб, восстановления VM, установки зависимостей, выяснения credentials или другой инфраструктурной рутины — сначала остановиться и передать подготовку среды дешёвому агенту.
- После того как дешёвый агент подтвердил готовность среды, дорогой исполнитель использует готовый стенд и не повторяет уже выполненную инфраструктурную диагностику без новой конкретной ошибки.
- Исключение: если сама инфраструктурная проблема является сложной инженерной задачей и дешёвый агент после разумной попытки не справился, её можно эскалировать на более сильную модель.

Практическая проверка перед назначением дорогой модели: **«Она сразу начнёт решать продуктовую задачу или сначала будет чинить окружение?»** Если второе — сначала подготовить окружение дешёвой моделью.

## Экономия лимитов

- Токены Claude и Codex нужно беречь.
- Gemini можно использовать до исчерпания доступного лимита; резервировать его не нужно.
- Muse и другие бесплатные/дешёвые модели использовать максимально для подходящей работы: инфраструктуры, VM, диагностики, исследования, повторных прогонов, review и других задач, где их качества достаточно.
- Если анализ, review, поиск ошибки, чтение diff или другая работа нормально решается бесплатным/дешёвым агентом (например Muse/DeepSeek) или отдельным ChatGPT-чатом, не тратить на неё Claude/Codex без причины.
- Codex сейчас не использовать как coding-agent: примерно последние 30% общего лимита зарезервированы для архитектора.
- Astra не использовать и не рекомендовать без отдельного нового решения владельца.
- Дорогую модель использовать только там, где её качество действительно даёт пользу: основная реализация после подготовленного окружения, сложная отладка, архитектурная развилка или задача, с которой более дешёвый исполнитель не справился.

## Git

- Перед работой всегда делать fresh fetch и проверять актуальные refs.
- Runtime-задача привязана к конкретному Code SHA; движение docs-ветки не меняет Code SHA автоматически.
- Не путать `origin` и приватный `dev`.
- Не плодить ветки без необходимости. После завершения волны отдельно чистить только доказанно ненужные refs/worktrees.
- Не промотить код только потому, что агент написал `DONE` или тесты зелёные.

## Где запускать Drawer и тесты

- Для VM-задач сначала использовать подготовленный `drawer-vm` preflight и готовую VM-инфраструктуру; не начинать общую диагностику VMware заново без новой конкретной ошибки.
- Бесплатные/дешёвые модели по возможности используют VM для runtime-прогонов, долгой диагностики и инфраструктурных проверок.
- Дорогим исполнителям можно использовать основную Windows владельца для безопасных runtime-проверок Drawer, если это экономит лимит и не затрагивает систему шире самого Drawer.
- Если тест меняет системные службы, реестр, драйверы, shell, VMware или создаёт заметный риск зависания/потери рабочего состояния — использовать VM независимо от стоимости модели.
- Repo-only проверки, чтение кода, diff, статическая проверка и другие действия, которые не запускают Drawer, можно делать без VM.
- Не запускать дорогого агента в длинный цикл VM-диагностики, если эту часть можно передать дешёвому исполнителю.

## Автономный цикл агента

Если пользователю/архитектору явно запущен автономный цикл конкретного агента:

1. Агент выполняет только разрешённую ему READY-задачу.
2. После завершения и публикации результата снова читает свежую `AGENT_BOARD.md`.
3. Если для него появилась следующая READY-задача — берёт её по правилам доски.
4. Если задач нет — не завершает автономный режим окончательно, а проверяет доску примерно каждые 5 минут.
5. Как только появляется подходящая READY-задача, продолжает работу.
6. Если возник блокер, требующий решения пользователя/архитектора, сообщает о нём вместо бессмысленного polling.

Это правило действует только для явно запущенного автономного цикла. Обычный разовый агент после своей задачи останавливается.

## Проверка

- Отчёт агента — подсказка, а не доказательство.
- Для кода проверять diff, базу, scope и существенные тесты.
- Для поведения окон, кромок, фокуса, анимации и multi-monitor важна ручная проверка владельца.
- После провала ручной проверки сначала разбирать конкретную регрессию, а не запускать цепочку новых рефакторингов.

## Продукт

- `PRODUCT_SPEC.md` и явные решения владельца имеют приоритет.
- `master` — рабочая отправная точка, но не эталон правильного поведения.
- Если непонятно, как функция должна вести себя, **спросить пользователя до изменения поведения**.
- Не превращать техническую гипотезу агента в новое продуктовое правило.

## Общение

Пользователю сообщать в первую очередь: что изменилось, что сломано, что нужно проверить или решить. Внутренние Run ID, SHA, названия seam-тестов и веток показывать только когда они реально помогают.
