# Прогон в виртуальной машине

Тесты Drawer захватывают рабочий стол: двигают окна, мышь и фокус. На
рабочей машине это значит, что во время прогона за ней нельзя работать —
и не из вежливости: физическая мышь перебивает `MouseMove` драйвера,
наведение на кромку не воспроизводится, `WinActivate` промахивается. Это
уже дважды давало ложные провалы.

VM решает обе задачи сразу: рабочий стол хоста свободен, а состояние
гостя откатывается снимком до чистого перед каждым прогоном.

## Что нужно один раз

**VirtualBox** — стоит (7.2.16, поставлен через `winget install Oracle.VirtualBox`).

**ISO Windows.** Свой. Рекомендуемый — Windows 11 Enterprise, оценочная
версия на 90 дней, с [Microsoft Evaluation Center](https://www.microsoft.com/evalcenter/evaluate-windows-11-enterprise).
Там форма регистрации перед скачиванием, поэтому файл (около 6 ГБ)
качаете вы. Ключ не нужен. Срок продлевается двумя перезапусками
счётчика примерно до 270 дней, дальше ВМ пересоздать.

Ключ от предустановленной Домашней для ВМ не годится — это OEM-лицензия
этой машины.

## Создание ВМ

```powershell
powershell -ExecutionPolicy Bypass -File test\vm\new-vm.ps1 -Iso D:\iso\win11-enterprise.iso
```

Скрипт создаёт машину (4 ГБ ОЗУ, 4 ядра, диск 64 ГБ, EFI, TPM 2.0,
Secure Boot — без них Windows 11 не ставится), включает **два экрана**,
запускает автоустановку и ждёт, пока в госте заработает управление. Это
20–40 минут, вопросов не задаётся. Потом кладёт в гостя
`AutoHotkey64.exe` с хоста — интерпретатор самодостаточен, ничего
скачивать внутри не надо, и сеть гостю для тестов не нужна вовсе.

Дальше два шага руками, которые скрипт печатает сам:

1. **Убедиться, что монитор 2 стоит слева от монитора 1.** Скрипт
   пытается сделать это с хоста (`controlvm setscreenlayout 1 on -1920 0 …`),
   но примет ли Windows отрицательное начало координат по подсказке
   драйвера — до первого прогона непроверено. Если нет, зайти в гостя и
   перетащить второй экран влево в параметрах дисплея.
2. **Снять снимок чистого состояния:**
   ```powershell
   VBoxManage snapshot "drawer-test" take чисто --pause
   VBoxManage controlvm "drawer-test" resume
   ```

Раскладка — не косметика. От того, что монитор 2 слева, зависит, какие
края внутренние: `M1/left` и `M2/right` смотрят на соседа, и именно на
них проверяется главный инвариант. На неправильной раскладке
`test\run.ps1` откажется работать — `layout.ahk` проверяет это до
запуска, так что молча неверных результатов не будет.

## Прогон

```powershell
powershell -ExecutionPolicy Bypass -File test\vm\run-in-vm.ps1 -Snapshot чисто
powershell -ExecutionPolicy Bypass -File test\vm\run-in-vm.ps1 -Only kromka
powershell -ExecutionPolicy Bypass -File test\vm\run-in-vm.ps1 -Suites all
```

Гость поднимается headless — на хосте не появляется ни одного окна.
Скрипт заливает свежий `src\drawer.ahk` и всю папку `test`, запускает
внутри `test\run.ps1`, забирает логи в `%TEMP%\drawer-vm-logs` и снимает
оба экрана гостя в PNG (в headless иначе не посмотреть, что там было).
Код возврата — код прогона.

`-Suites all` требует, чтобы в госте стояли VS Code, Telegram и Chrome:
набор `apps` проверяет именно их. На чистой ВМ он работать не будет,
пока их туда не поставить.

## Чего эти скрипты не умеют

Они написаны по справке `VBoxManage --help` версии 7.2 — все ключи и
формы команд сверены, — но **целиком ни разу не выполнялись**: для этого
нужен ISO. Первый запуск стоит делать с `-Gui`, чтобы видеть установку
своими глазами.

Остальное проверено на хосте: сам стенд (`test\run.ps1`) прогнан на
наборах `extra` и `quiet` — 11/11 и 7/7, окон за экранами не осталось,
код возврата 0.
