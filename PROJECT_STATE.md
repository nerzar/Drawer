# PROJECT_STATE — Drawer

Актуально на 2026-09-06, рабочая линия `wip/slots-parity`.
История решений находится в `docs/03-решения.md`, история ручной приёмки —
в `docs/04-чек-лист-приёмки.md`.

## Назначение

Drawer — Windows-утилита на AutoHotkey v2. Она назначает окнам слоты
1–9, паркует их за пределами виртуального рабочего стола и возвращает по
хоткею, активации через Alt+Tab/панель задач или щелчку по экранной
кромке.

Версия приложения — `0.1.2-beta`. Собранный `Drawer.exe` самодостаточен;
AutoHotkey требуется только для разработки и тестов.

### Упаковка WebView Settings

`build/build.ps1` собирает фронтенд из `settings-ui/` в один
`src/webview/web/index.html` и вшивает в exe его и
`WebView2Loader.dll` (`FileInstall`, см. `src/webview/SettingsWebAssets.ahk`).
На машине пользователя не нужны ни Node, ни `npm run build`, ни папка
`src/webview/web`: при первом открытии настроек оба файла распаковываются
в `%TEMP%\Drawer-WebView-<версия>`, откуда их берут виртуальный хост
WebView2 и `DllCall`. Обычный запуск ящика не пишет на диск ничего.

Единственная внешняя зависимость — Microsoft Edge WebView2 Runtime
(системный компонент ~150 МБ, ящик его не носит). Его отсутствие
проверяется до создания окружения и сообщается текстом со ссылкой;
native Settings при этом продолжает работать.

Две ловушки Ahk2Exe, на которые уже наступили и которые закрыты
проверками в `build/build.ps1`:

- `FileInstall` распознаётся только как начало инструкции. Запись
  `try FileInstall(...)` одной строкой компилятор пропускает молча:
  сборка успешна, ассета в exe нет, распаковка даёт файл нулевой длины.
- По размеру exe этого не видно — текст исходников сам по себе больше
  нагрузки. Поэтому сборка ищет кусок каждого ассета в exe побайтово.

## Архитектура

Production-код разделён на модули:

- `src/Slots.ahk` — модель слота, реестр и общие операции над слотами;
- `src/drawer.ahk` — загрузка `config.ini`, оконная модель
  (показ, парковка, геометрия, фокус), foreground-hook, кромки, native
  Settings и трей;
- `src/webview/` — WebView Settings: транспорт WebView2, JSON-протокол и
  семантический порт поверх того же Settings backend.

### Slot как runtime-сущность

`Slot` — центральная сущность рантайма и единственный источник истины о
слоте. Идентичность слота — его НОМЕР 1…9: он же имя секции в
`config.ini` (`[slot3]`, `[dynamicSlot3]`) и часть хоткея, поэтому
переживает перечитывание файла. Позиционной идентичности (индекса в
массиве) в программе больше нет.

Запись реестра:

```text
Slot.n         1…9 — идентичность слота
Slot.perm      конфигурация [slotN]; 0 — слот динамический
Slot.override  надстройка [dynamicSlotN] или 0
Slot.window    окно слота в этой сессии
```

Permanent и dynamic — два lifecycle одной сущности, и `window` у них
одно поле: у постоянного это кэш найденного по `exe` (+ необязательному
`cls`) окна, который можно потерять и восстановить, у динамического —
сама привязка, сделанная пользователем и не переживающая перезапуск.
Различается не хранение, а разрешение: пустой `window` у постоянного
означает «поискать по exe», у динамического — «слот пуст».

Реестр — проекция `config.ini` плюс привязки текущей сессии, а не второе
хранилище. `Slots.Apply(cfg, prevPerm)` — единственное место, где
меняются род и конфигурация слота, и, кроме `SlotRelease` и
`SlotClearDynamic`, единственное, где окно возвращается домой.

Внешние потребители — хоткеи, кромки, native Settings и WebView-порт —
ходят через функции `src/Slots.ahk` (`SlotIsPermanent`, `SlotPerm`,
`SlotOverride`, `SlotDefaults`, `SlotCfg`, `SlotBehavior`,
`SlotPermList`, `SlotWindow`, `SlotCapture`, `SlotOf`, `SlotBound`,
`SlotStatus`, `ToggleSlot`, `SlotFocus`, `SlotBind`, `SlotRelease`,
`SlotClearDynamic`) и внутреннего устройства реестра не знают. Вниз
модуль зависит только от оконной модели: `Release`, `FindWindow`,
`ToggleWindow`, `FocusWindow`, `PickActive`, `WindowManaged`,
`WindowParked` — плюс `Notify`-свободные мелочи (`Opt`, `HandlesSync`).

Оконная модель осталась отдельной и ключуется HWND, а не слотом:

```text
state[]         HWND → исходная и рассчитанная геометрия
watched[]       HWND → настройки окна под наблюдением hideOnBlur
iconUriCache[]  HWND → data-URI иконки окна
handles[]       номер слота → Gui кромки
```

Загрузка конфига отделена от рантайма: `LoadConfig(path, &diags)`
возвращает объект конфигурации и ничего не присваивает, `ConfigApply()`
проецирует его общую часть в глобалы (`animMs`, `animSteps`, `blurMs`,
`handlesOn`, `HANDLE_BG`), `Slots.Apply()` — слоты в реестр.

### Settings integration seam

В `4844486` native Settings переведён на общий Save pipeline:
`SettingsGeneralPlan` / `SettingsSlotsPlan` → `SettingsApplyPlan` →
`SettingsPersistVerified` → `SettingsReconcileRuntime`. Планирование не
пишет файл и не освобождает окна; persistence пишет и сверяет INI;
reconciliation перечитывает файл после выхода из persistence и сохраняет
постоянные bindings по номеру слота и неизменным `exe`/`cls`.

C5 сделал загрузку конфига пригодной для headless service: `LoadConfig` и
`IniBool` окон не открывают, а складывают замечания в `diags`; показывает
их вызывающий — `ConfigDiagShow` при старте и native после Save. Там же
появилась общая backend-валидация семантического входа
(`SettingsEdgeIn`/`SettingsMonitorIn`/`SettingsAccentIn`/`SettingsBoolIn`/
`SettingsTextIn` плюс проверка номера и типа слота): то, что раньше
гарантировали DropDownList, чекбокс, диалог цвета и однострочный Edit,
теперь проверяет backend, потому что порт таких гарантий не даёт.

`SettingsHotkeyIn` закрывает последнее поле слота, остававшееся без
проверки, — `focusHotkey`. Синтаксис спрашивается у самого AutoHotkey
(регистрация выключенной и в контекст, который никогда не истинен),
а не разбирается вторым списком модификаторов и имён клавиш. Проверяется
только НОВОЕ значение: негодный хоткей, уже записанный в файл, не
запирает правку соседних полей. Пустое значение — «у слота нет хоткея»,
пробелы по краям снимаются (Р23).

Если persistence возвращает `mayHavePersisted=true`, reconciliation
выполняется и при ошибке. Откат частичной записи не обещается.
В `a39f543` ошибка чтения при сверке удаления больше не считается
подтверждением удаления; динамический binding освобождается только при
фактическом переходе в Permanent после `LoadConfig`.

После выделения реестра `SettingsReconcileRuntime` своей логики слотов не
содержит: она перечитывает файл, отдаёт общую часть `ConfigApply` и
слоты — `Slots.Apply(cfg, slotPlan.prevPerm)`. Снимок постоянных
привязок (`slotPlan.prevPerm`) по-прежнему берётся планом ДО любой
дисковой операции; список `slotPlan.touched` стал не нужен и удалён —
переход в Permanent подтверждает сам перечитанный файл, а не намерение
правки.

В C4 outcome доведён до полного контракта Save. `SettingsPersistVerified`
возвращает код `write_failed`/`verify_failed` вместо одного текста;
`mayHavePersisted` поднимается только завершившейся дисковой операцией.
`SettingsApplyPlan` ловит исключения обеих стадий — из GUI-колбэка Apply/OK
ничего не вылетает — и возвращает `runtimeReloaded`, `changedSlots`,
`restartRequired` и канонический `state` (`SettingsStateSnapshot`), причём
`state` только после успешного reload. Повтор запрещён единственным случаем:
диск тронут, а перечитать его не удалось. Удаление `[dynamicSlotN]` теперь
сверяется чтением, как и удаление `[slotN]`.

### WebView Settings: вкладка General

Код лежит в `src/webview/`: транспорт (`SettingsWebView.ahk` поверх
вендоренного WebViewToo), протокол (`SettingsJsonBridge.ahk`), codec
(`Json.ahk`), семантический порт (`SettingsPort.ahk`) и склейка с
рантаймом (`SettingsWebHost.ahk`). Порт зовёт тот же backend C1–C5;
второй реализации записи нет.

Через мост проходит вся вкладка General — те же десять ключей, что
правит native: `[dynamic]` width/edge/monitor/activateOnShow/hideOnBlur и
`[general]` handles/animMs/animSteps/blurMs/accent. Черновиком владеет
Vue (`settings-ui/src/bridge/general.ts`), применённым состоянием — AHK:
успешный Apply/ОК возвращает канонический state, и он же становится новым
baseline. Неудачный Save черновик не трогает — заново набирать не
приходится.

Dirty-семантика вся на настоящем пути. Отмена и системный крестик
присылают черновик, порт сравнивает его с применённым состоянием тем же
`SettingsGeneralPlan`, которым делает Save, и отвечает `closed:false`,
если терять есть что. Вопрос задаёт страница, а не MsgBox из моста:
модальное окно на стороне AHK остановило бы очередь сообщений WebView и
дало бы сработать таймауту решения.

Slots read-only + live status подключены к production: все девять строк
и детали берутся из canonical DTO, permanent value и dynamic effective
включают реальные настройки слота. `slot.watchStatus` включает 400-мс
опрос существующего `SlotStatus(n)` через порт; при входе отправляются
все статусы, затем только изменения enum/title через `slot.statusChanged`.
Vue меняет статус нужной строки, не перечитывая Settings и не трогая
General draft. Уход со вкладки выключает таймер, закрытие уничтожает его.

Существующие permanent Slots редактируются через отдельный draft из
canonical DTO. Apply/OK отправляют изменённые config values в `slotEdits`:
порт переводит их в `SettingsSlotsPlan → SettingsApplyPlan`, без второго
пути записи. Success заменяет baseline и оба draft ответом AHK; validation
сохраняет ввод и показывает сообщение/field. Dirty-close проверяет General
и Slots общими планами, а live status не касается slot draft.

Mock остался в заголовке окна и About. Native Settings сохранён.
`picker.exe` и `picker.window` используют общий production picker с native
Settings. EXE/window result меняет только draft, Cancel ничего не меняет.
Общий gate исключает повторный picker и блокирует Save/bind/release;
owner отключён на время диалога. Bridge выходит из WebMessageReceived до
модального вызова и откладывает Dispose/Destroy до выхода picker из стека.
Native Close также отложен; оба UI защищают поздний write-back. Picker RPC
не имеет таймаута пользовательского выбора; закрытие отменяет ожидание.

`slot.bind` и `slot.release` работают через порт: они зовут те же
`SlotBind`/`SlotRelease`, что и хоткеи, и возвращают статус со снимком
canonical. Утверждённого UI у них нет, поэтому во вкладке нет и кнопок:
из формы эти операции не вызываются, а smoke зовёт их протоколом.

Вкладка Slots показывает утверждённый макет: строка списка с номером,
аватаркой, точкой состояния и родом слота; форма постоянного слота с
кнопками-иконками «Обзор…»/«Окно…» и классом окна в подсказке; таблица
динамического слота с источником каждого значения. Кнопки смены рода
стоят на своём месте выключенными: порт принимает правки только
существующих постоянных слотов. Окно 1060x700 — размер, при котором
макет виден целиком; уже — поля ужимаются сами.

Structured field error доводит до контрола. `error.field` — адрес: App
переключает вкладку, SlotsView выбирает слот и подсвечивает поле
(`settings-ui/src/bridge/fieldError.ts`, чистые проверки в `npm test`).
Путь поля в сообщении не показывается: там стоит название контрола,
одно на обе стороны — `SettingsSlotFieldLabel()`.

C6 выполнен. Остаётся conversion; dynamic Slots правятся только сменой
рода, которой пока нет.

### Канонический state и черновики

Канонический state приходит четырьмя каналами: загрузка, Save,
`slot.bind`/`slot.release` и `state` из ошибки частичной записи. Правила
их совместимости собраны в `settings-ui/src/bridge/canonical.ts` и
проверяются отдельно от Vue (`cd settings-ui && npm test`):

- каждый запрос за canonical берёт номер до `await`; побочный ответ
  применяется, только если он новее последнего принятого. Полагаться на
  порядок доставки нельзя — у picker ответ уходит из таймера;
- снимок Save и загрузки сделан после записи, поэтому применяется всегда
  и закрывает дорогу ответам, выданным до него;
- успешный Save пересобирает черновики из применённого состояния;
- замена canonical мимо Save черновики согласует: слот остался того же
  рода — черновик сохраняется, даже грязный; сменил род — старый
  черновик описывает уже не тот слот и выбрасывается.

Последнее правило заведено до conversion, а не после: смена рода — это
единственный случай, когда черновик слота перестаёт значить то, что
значил.

## Инварианты

- У слота одна runtime-запись: структур, способных описать один и тот же
  слот по-разному, в программе нет.
- Идентичность слота — его номер, а не позиция в каком-либо списке.
- Динамический слот хранит конкретный HWND, а не приложение, и эта
  привязка живёт только до перезапуска.
- Постоянный слот ищет окно по `exe` и необязательному `cls`.
- Постоянный и динамический не бывают одним слотом одновременно.
- Припаркованное окно остаётся системно видимым и доступным из панели
  задач; `WinHide` не используется.
- Парковка выполняется за границей всего виртуального рабочего стола.
- На внутреннем крае между мониторами анимация отключается, чтобы окно
  ни одним кадром не появлялось на соседнем экране.
- Штатный выход и освобождение слота возвращают окно в исходную позицию.
- `config.ini` — единственное постоянное хранилище настроек.
- Settings пишет только по Apply/OK, отдельными ключами, затем читает
  записанное обратно. Cancel, закрытие Settings и выход не сохраняют.

## Функциональность

- Девять постоянных или динамических слотов.
- Отдельные monitor/edge/width/activateOnShow/hideOnBlur для слота.
- Индивидуальные `[dynamicSlotN]` поверх `[dynamic]`.
- Анимация четырёх краёв и multi-monitor геометрия.
- Автоматическая парковка по потере фокуса.
- Возврат припаркованного окна при системной активации.
- Экранные кромки с иконкой, номером и реакцией на курсор.
- Settings для General и постоянных слотов, включая выбор exe/окна и
  смену типа слота.
- Дедупликация одинаковых TrayTip в течение четырёх секунд.

## Хоткеи

| Хоткей | Действие |
|---|---|
| `Ctrl+Alt+1…9` | показать или убрать слот |
| `Ctrl+Alt+Shift+1…9` | назначить активное окно динамическому слоту |
| `Ctrl+Alt+0` | очистить все динамические слоты |
| `Ctrl+Alt+Shift+0` | выйти и вернуть окна |
| `focusHotkey` | показать при необходимости и сфокусировать постоянный слот |

Основные хоткеи регистрируются через клавиатурный хук (`$`), а не через
`RegisterHotKey`.

проверки исходников `src/drawer.ahk` и `src/Slots.ahk`.
Точка 17 — модель проекции конфига на реестр: неизменная identity
сохраняет захваченное окно, смена `exe`/`cls` и потеря постоянного рода
возвращают его домой, подтверждённый переход в Permanent отпускает
динамическую привязку, а неподтверждённый (partial failure) — нет.
Точка 18 — контракт хоткея постоянного слота: синтаксис AutoHotkey
принимается, понятная человеку запись отвергается, пустое значение
ошибкой не считается, пробелы снимаются, проверка не ломает уже
назначенный хоткей, `focusHotkey` переживает запись и чтение INI, а
неизменённое негодное значение не мешает править соседнее поле.
Это не поведенческая приёмка S4. VM/full suite не запускался.

## Подтверждённые ограничения

- На внутреннем крае между мониторами нет плавной анимации.
- Кромка занимает 22 пикселя рабочей области и может быть перекрыта
  fullscreen/AlwaysOnTop-окном.
- Частые нажатия хоткея выполняются очередью.
- Аварийное завершение оставляет припаркованные окна за экраном; новый
  запуск способен найти и вернуть постоянные окна.
- `config.ini` должен сохранять UTF-16 LE для кириллицы.
- Отдельного хоткея очистки одного динамического слота нет.
- Постоянный слот с несколькими окнами одного процесса выбирает самое
  большое подходящее окно.
- `focusHotkey` регистрируется один раз при старте и по номеру слота (C1).
  Правка самого хоткея вступает в силу только после перезапуска; Save
  сообщает такие слоты в `restartRequired`.
- Save не транзакционный: General может сохраниться раньше ошибки Slots.
  Rollback не обещается; частичная запись возвращается как `write_failed`
  или `verify_failed` с `mayHavePersisted`, а не как успех.

## Оставшиеся риски и пробелы

- Смешанный DPI мониторов не проверен.
- Сочетание `hideOnBlur=true` и `activateOnShow=false` не покрыто
  отдельным тестом.
- Расхождение файла и рантайма после неудачного reload не устраняется
  автоматически: outcome сообщает `runtimeReloaded=false` и запрещает
  повтор, но привести рантайм в соответствие может только перезапуск.
- Негодный `focusHotkey`, уже лежащий в `config.ini`, по-прежнему
  всплывает сообщением при старте — по одному на слот. Новая правка
  такого значения через Settings невозможна (`SettingsHotkeyIn`), но
  файл, набранный руками до этой проверки, программа не чинит сама.
- Планы по-прежнему сравнивают с рантаймом, а не с файлом
  (`SettingsLive` — общие глобалы, `SettingsLiveSlot` — реестр): точечная
  запись сравнивает с тем, чем программа пользуется прямо сейчас. Это
  сознательное решение, а не пробел: умолчания живут в `LoadConfig`, и
  дублировать их в планах не приходится.
- Оконная модель (`state`, `watched`, `Show`/`Hide`/геометрия), кромки и
  native Settings по-прежнему лежат в `src/drawer.ahk` одним файлом.
  Границы у них есть, физического разделения — нет.

## Правила изменений

- Не заменять парковку на `WinHide` и не анимировать окно через соседний
  монитор.
- Не убирать `Critical()` и фильтры служебных окон без целевых тестов
  фокуса и гонок.
- Не регенерировать `config.ini` целиком: комментарии пользователя и
  отсутствующие ключи должны сохраняться.
- После изменения геометрии, фокуса или кромок запускать соответствующий
  целевой набор в VM, а не весь suite на рабочем столе.
- После изменения Settings отдельно проверять отсутствие записи на
  Cancel/Close и возврат окон при смене типа слота.

## Согласованное направление

Целевая архитектура — модульный монолит с центральной runtime-сущностью
`Slot`, явными границами модулей и единым API действий над слотами.
Сама сущность и её реестр выполнены (`src/Slots.ahk`, Р22); разделение
оконной модели, кромок и Settings по модулям остаётся.
Текущие девять слотов и связь номера с хоткеем остаются действующим
поведением до отдельного этапа расширения модели.

Перед production WebView выполняются ограниченные seams C1–C5:
stable Slot ID → service-window registry → structured SlotStatus →
Save outcome → headless validation/config. Затем подключается WebView
bridge, после него выполняется C6 native picker parity fix.
Порядок принят в Р20 (`docs/03-решения.md`), критерии этапов находятся
в `docs/05-план-работ.md`. Полная модульная декомпозиция не блокирует bridge;
произвольные слоты и новые действия остаются после структурного этапа.
