# PROJECT_STATE — Drawer

Актуально для production snapshot `a39f543` на 2026-09-05.
История решений находится в `docs/03-решения.md`, история ручной приёмки —
в `docs/04-чек-лист-приёмки.md`.

## Назначение

Drawer — Windows-утилита на AutoHotkey v2. Она назначает окнам слоты
1–9, паркует их за пределами виртуального рабочего стола и возвращает по
хоткею, активации через Alt+Tab/панель задач или щелчку по экранной
кромке.

Версия приложения — `0.1.2-beta`. Собранный `Drawer.exe` самодостаточен;
AutoHotkey требуется только для разработки и тестов.

## Архитектура

Production-код находится в одном файле `src/drawer.ahk` и разделён на
три подсистемы:

1. Загрузка `config.ini`, слоты, показ/парковка, foreground-hook и
   управление фокусом.
2. Кромки припаркованных окон: собственные Gui-окна, иконки, наведение и
   щелчок.
3. Settings: General, список слотов, live-статус, выбор exe/окна,
   редактирование постоянных слотов и Dynamic ↔ Permanent.

Основное состояние хранится в глобальных структурах:

```text
apps[]          конфигурации постоянных слотов
managed[]       номер слота → захваченный HWND
state[]         HWND → исходная и рассчитанная геометрия
watched[]       окна под наблюдением hideOnBlur
permSlots[]     номер слота → индекс apps (живёт только до LoadConfig)
dynSlots[]      номер слота → HWND
dynamicSlots[]  номер слота → индивидуальные динамические настройки
handles[]       номер слота → Gui кромки
```

### Settings integration seam

В `4844486` native Settings переведён на общий Save pipeline:
`SettingsGeneralPlan` / `SettingsSlotsPlan` → `SettingsApplyPlan` →
`SettingsPersistVerified` → `SettingsReconcileRuntime`. Планирование не
пишет файл и не освобождает окна; persistence пишет и сверяет INI;
reconciliation перечитывает файл после выхода из persistence и сохраняет
постоянные bindings по номеру слота и неизменным `exe`/`cls`.

C5 сделал загрузку конфига пригодной для headless service: `LoadConfig` и
`IniBool` окон не открывают, а складывают замечания в `diags`; показывает
их вызывающий — `ConfigDiagShow` при старте и native после Save. Там же
появилась общая backend-валидация семантического входа
(`SettingsEdgeIn`/`SettingsMonitorIn`/`SettingsAccentIn`/`SettingsBoolIn`/
`SettingsTextIn` плюс проверка номера и типа слота): то, что раньше
гарантировали DropDownList, чекбокс, диалог цвета и однострочный Edit,
теперь проверяет backend, потому что порт таких гарантий не даёт.

Если persistence возвращает `mayHavePersisted=true`, reconciliation
выполняется и при ошибке. Откат частичной записи не обещается.
В `a39f543` ошибка чтения при сверке удаления больше не считается
подтверждением удаления; динамический binding тронутого слота освобождается
только при фактическом переходе в Permanent после `LoadConfig`.

В C4 outcome доведён до полного контракта Save. `SettingsPersistVerified`
возвращает код `write_failed`/`verify_failed` вместо одного текста;
`mayHavePersisted` поднимается только завершившейся дисковой операцией.
`SettingsApplyPlan` ловит исключения обеих стадий — из GUI-колбэка Apply/OK
ничего не вылетает — и возвращает `runtimeReloaded`, `changedSlots`,
`restartRequired` и канонический `state` (`SettingsStateSnapshot`), причём
`state` только после успешного reload. Повтор запрещён единственным случаем:
диск тронут, а перечитать его не удалось. Удаление `[dynamicSlotN]` теперь
сверяется чтением, как и удаление `[slotN]`.

Production WebView bridge ещё не подключён. `settings-ui/` — Vue-фронтенд
с mock state/bridge. Принятый integration-контракт перенесён из spike/review
в `docs/settings-integration-layer.md`; архитектурный gate Claude — GO.
GO подтверждает направление и порядок подготовки, а не готовность bridge.

## Инварианты

- Динамический слот хранит конкретный HWND, а не приложение.
- Постоянный слот ищет окно по `exe` и необязательному `cls`.
- Припаркованное окно остаётся системно видимым и доступным из панели
  задач; `WinHide` не используется.
- Парковка выполняется за границей всего виртуального рабочего стола.
- На внутреннем крае между мониторами анимация отключается, чтобы окно
  ни одним кадром не появлялось на соседнем экране.
- Штатный выход и освобождение слота возвращают окно в исходную позицию.
- `config.ini` — единственное постоянное хранилище настроек.
- Settings пишет только по Apply/OK, отдельными ключами, затем читает
  записанное обратно. Cancel, закрытие Settings и выход не сохраняют.

## Функциональность

- Девять постоянных или динамических слотов.
- Отдельные monitor/edge/width/activateOnShow/hideOnBlur для слота.
- Индивидуальные `[dynamicSlotN]` поверх `[dynamic]`.
- Анимация четырёх краёв и multi-monitor геометрия.
- Автоматическая парковка по потере фокуса.
- Возврат припаркованного окна при системной активации.
- Экранные кромки с иконкой, номером и реакцией на курсор.
- Settings для General и постоянных слотов, включая выбор exe/окна и
  смену типа слота.
- Дедупликация одинаковых TrayTip в течение четырёх секунд.

## Хоткеи

| Хоткей | Действие |
|---|---|
| `Ctrl+Alt+1…9` | показать или убрать слот |
| `Ctrl+Alt+Shift+1…9` | назначить активное окно динамическому слоту |
| `Ctrl+Alt+0` | очистить все динамические слоты |
| `Ctrl+Alt+Shift+0` | выйти и вернуть окна |
| `focusHotkey` | показать при необходимости и сфокусировать постоянный слот |

Основные хоткеи регистрируются через клавиатурный хук (`$`), а не через
`RegisterHotKey`.

## Тестирование

Точка входа — `test/run.ps1`. Стенд управляет окнами, фокусом и мышью,
поэтому полные прогоны выполняются только в изолированной VM. Требуется
два монитора: DISPLAY2 слева от DISPLAY1.

Стандартный `safe` содержит 13 наборов:

```text
geom behav invar quiet kromka extra off
slots life load restart ghost setstat
```

`apps` и `browser` требуют установленных настоящих приложений. Полный
перечень и назначение наборов находятся в `test/README.md`.

`setstat` использует тестовые F11/F12-хоткеи, внедряемые во временную
копию исходника. В VM эта инструментация работала нестабильно; отсутствие
дампа пока классифицируется как дефект стенда. Покрытия нового S4
(редактирование и конвертация слотов) отдельным драйвером нет.

VM-оркестратор находится в `test/vm/` и использует VMware Workstation
через `vmrun`. Подтверждён end-to-end прогон набора `off`: 10/10,
артефакты вернулись на хост, VM выключилась штатно. `apps`/`all` в этой
VM не подтверждены.

`test/narrow/settings-seam.ahk` — 119/119 на host: копии чистых функций
(`SettingsVerifyDeleted`, `IsServiceWindow`, `SlotWindow`/`SlotStatus`,
решающая логика `SettingsApplyPlan`, валидаторы входа, `IniBool`), сверка
значений и умолчаний на временном INI и статические проверки исходника.
Это не поведенческая приёмка S4. VM/full suite для C1–C5 не запускался.

## Подтверждённые ограничения

- На внутреннем крае между мониторами нет плавной анимации.
- Кромка занимает 22 пикселя рабочей области и может быть перекрыта
  fullscreen/AlwaysOnTop-окном.
- Частые нажатия хоткея выполняются очередью.
- Аварийное завершение оставляет припаркованные окна за экраном; новый
  запуск способен найти и вернуть постоянные окна.
- `config.ini` должен сохранять UTF-16 LE для кириллицы.
- Отдельного хоткея очистки одного динамического слота нет.
- Постоянный слот с несколькими окнами одного процесса выбирает самое
  большое подходящее окно.
- `focusHotkey` регистрируется один раз при старте и по номеру слота (C1).
  Правка самого хоткея вступает в силу только после перезапуска; Save
  сообщает такие слоты в `restartRequired`.
- Save не транзакционный: General может сохраниться раньше ошибки Slots.
  Rollback не обещается; частичная запись возвращается как `write_failed`
  или `verify_failed` с `mayHavePersisted`, а не как успех.

## Оставшиеся риски и пробелы

- Смешанный DPI мониторов не проверен.
- Сочетание `hideOnBlur=true` и `activateOnShow=false` не покрыто
  отдельным тестом.
- Расхождение файла и рантайма после неудачного reload не устраняется
  автоматически: outcome сообщает `runtimeReloaded=false` и запрещает
  повтор, но привести рантайм в соответствие может только перезапуск.
- Синтаксис `focusHotkey` backend не проверяет: поле и в native — обычный
  однострочный Edit, гарантий не дававший. Негодная комбинация всплывает
  сообщением при следующем старте, как и раньше.
- Планы по-прежнему читают runtime globals (`SettingsLive`,
  `SettingsLiveSlot`): точечная запись сравнивает с тем, чем программа
  пользуется. Отдельного config-объекта у backend нет.

## Правила изменений

- Не заменять парковку на `WinHide` и не анимировать окно через соседний
  монитор.
- Не убирать `Critical()` и фильтры служебных окон без целевых тестов
  фокуса и гонок.
- Не регенерировать `config.ini` целиком: комментарии пользователя и
  отсутствующие ключи должны сохраняться.
- После изменения геометрии, фокуса или кромок запускать соответствующий
  целевой набор в VM, а не весь suite на рабочем столе.
- После изменения Settings отдельно проверять отсутствие записи на
  Cancel/Close и возврат окон при смене типа слота.

## Согласованное направление

Целевая архитектура — модульный монолит с центральной runtime-сущностью
`Slot`, явными границами модулей и единым API действий над слотами.
Текущие девять слотов и связь номера с хоткеем остаются действующим
поведением до отдельного этапа расширения модели.

Перед production WebView выполняются ограниченные seams C1–C5:
stable Slot ID → service-window registry → structured SlotStatus →
Save outcome → headless validation/config. Затем подключается WebView
bridge, после него выполняется C6 native picker parity fix.
Порядок принят в Р20 (`docs/03-решения.md`), критерии этапов находятся
в `docs/05-план-работ.md`. Полная модульная декомпозиция не блокирует bridge;
произвольные слоты и новые действия остаются после структурного этапа.
